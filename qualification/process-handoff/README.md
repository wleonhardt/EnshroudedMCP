# Process handoff qualification

Optional Windows-only, standard-library Python qualification for ordinary process observation around a client launch. It is separate from the game SDK and MCP dispatch. The helper never starts or stops a process. Only the fixtures start their own Python processes; they never select a game, access credentials, use desktop input or capture a screen.

From the repository root:

```powershell
python -B -m unittest discover -s qualification/process-handoff -p test_*.py -v
```

The caller must retain the `Popen` object it created while `launcher_facts` reads the process. Windows creation time is read at full FILETIME precision through that exact held CreateProcess handle, with no PID reselection after exit. This Windows-only qualification borrows CPython Popen's handle as supplied by the tested Python 3.15 implementation; it is not a portable launcher API. [Win32 documents that process handles remain valid until closed, including after termination](https://learn.microsoft.com/en-us/windows/win32/procthread/process-handles-and-identifiers). A successful exit has an explicit exit code, including actual exit 259; it is not inferred from a PID disappearing. Querying the image of an already exited process can fail even while creation time remains available. Requested and independently observed executable paths are separate fields. A missing exited image stays null; a live image query failure refuses. The existing strict live-process observer is unchanged.

The direct path requires the live identity to match the initial PID, creation time and requested executable. A handoff requires initial exit 0, an unchanged preexisting parent identity and expected parent image, a distinct new child at the expected image within the bounded creation interval, and independently observed parent linkage. CIM contributes PID, parent PID and path only. Its datetime representation never replaces or supplies a tolerance for exact Win32 creation comparisons. A separate listener check requires one matching loopback address, port and owner PID. These observations cannot authenticate a remote peer or prove game state.

The actual fixture starts one Python launcher whose output triggers an already running owned Python parent to start one child. The launcher object stays retained through exit and observation. The child opens a disposable loopback listener and waits for owned stdin closure. Win32 identities, CIM linkage and kernel listener ownership are observed independently. All owned processes exit normally; waits are bounded and fixtures use hidden windows. Direct and exited-launcher cases run separately. Refusals include a one-tick parent change, wrong parent/image, stale or late child, unsuccessful initial exit, non-loopback binding, duplicate listeners, wrong port and wrong owner.

The original six-method checkpoint includes actual exited children with codes 0, 7 and 259. The module uses the project's existing `scripts/process_exit.py` Win32 query functions and changes none of its callers. Python and OS behavior are qualified on the tested Windows host only. No real Steam handoff, game launch, provider load, Menu, MCP read, Join/Leave, character identity, inventory, rendering or adoption is accepted by this fixture. A game trial still needs its separately reviewed source/binary/rollback closure and explicit runtime exception. Decision 0103 remains consumed after the stopped trial in decision 0104.


## Retain observations before launch-outcome refusal

`checked_launcher_facts(process, requested_executable, record)` reads through the same caller-held handle, passes a copy to the caller's evidence writer, then refuses an observed nonzero exit. A writer exception propagates before any sample is returned. Running and successful-exit samples still require the existing independent identity/listener/Menu gates; this helper grants no launch, retry or binding authority. It never starts or stops a process. A successful callback means that callback returned, not a filesystem sync or hardware-durability guarantee.

The retention checkpoint's eight methods include real Python exits 0/7/259, exclusive sample writes, independent file reads after the original Popen reference is released, and write-collision refusal without overwriting prior evidence. Exact sample files are retained under ignored `target/process-handoff-samples/`, including on failure. They are private owned-process observations, not game data or publication artifacts.

The inactive [controller fragment](retain-launch-samples.patch) records sequential create-new samples with stage `launcher_outcome` and an observation-time monotonic timestamp before checking the outcome. That timestamp is local sample timing, not wall time or a replacement for Win32 creation time. A private thirteen-case controller model reproduces the old loss, then verifies retained nonzero samples, unchanged once-only guards and write-failure refusal. The private operational controller is not published; public tests independently qualify the helper against owned Python processes. This fragment is not an executable game controller or a complete runtime closure.

## Explicit launcher and effective-image roles

Valve documents `-applaunch <appID>` as a Steam launch parameter. Steamworks also describes a restart-through-Steam helper whose original process may terminate while a new copy starts. These published mechanisms motivate inspecting a Steam-mediated launch route; neither identifies Enshrouded's retained exit53 or proves that this game uses that helper. No Steam API, game process, DRM stub or credential is touched by this qualification.

`handoff_identity(..., expected_effective_executable=...)` can now name a separate absolute expected child image. Omission preserves the original same-image rule. Empty, relative and non-string expectations refuse; child image, unchanged parent identity, full Win32 creation ordering, CIM linkage and listener checks remain exact. Initial nonzero exits, including53, still refuse. The option validates observations; it starts nothing and supplies no native game executor.

Ten optional methods now include an actual hidden `cmd.exe /d /c echo launch` process whose fixed output asks the owned Python parent to create its Python child. The original cmd handle is retained through observation; the default image rule refuses, and the explicit expected Python image passes with independent parent/listener observations. Only that exclusively owned command process may be killed on a failed bounded fixture wait. Other cases verify malformed expectations, wrong image/parent/order/linkage and nonzero refusal. No Steam client invocation occurs.

Future orchestration must separately qualify one reviewed Steam request, successful initial exit, the intended effective image, target process/loopback ownership and fresh Menu. It must not assume that a running Steam parent forwards the invoking process's environment. Existing consumed controllers and approvals remain unchanged; this helper feature authorizes no game retry.

Sources: [Valve launch parameter documentation](https://developer.valvesoftware.com/wiki/Command_line_options_(Steam)) and [Steamworks restart documentation](https://partner.steamgames.com/doc/api/steam_api#SteamAPI_RestartAppIfNecessary).
